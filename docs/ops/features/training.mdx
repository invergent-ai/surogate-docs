# Training Runs

A Training Run is a model fine-tune scheduled on your compute. Surogate orchestrates the run via the [Surogate Trainer](/old-docs) — the LLM training library at the platform's core. When the run completes, the weights land in your Hub and you can promote them to a deployable Model.

Two training paradigms, both run from the same surface:

- **SFT** — supervised fine-tuning. Pair `(prompt, completion)` examples; the model learns to produce the completion.
- **GRPO** — group relative policy optimisation. RL training against a reward model or an environment.

## When to run training

- You've captured a few hundred clean sessions and want a model that does that specific job better than a generalist.
- Your inference bill on a frontier model is high enough that a smaller fine-tuned model would pay for itself.
- You need a specific capability (math reasoning, code review, an internal style) that a generalist doesn't reliably deliver.
- You have a verifiable reward signal (test pass-rate, environment success) and want to push past what SFT can reach — that's a GRPO run.

## Start a run

<Figure
  src="/img/screenshots/training-new-run.png"
  alt="New Training Run wizard with the Kind toggle (SFT / GRPO), Name, Short description, Long description fields, and the per-kind config below"
  caption="New Run — pick kind first; the form below adapts to SFT vs GRPO."
/>

Train → Training Runs → **New Run**. The wizard has two tabs.

### RUN tab

The metadata tab. Three text fields:

- **Run name** — display label and `runId` prefix. Pick something you'll recognise on a metrics dashboard six months from now.
- **Experiment** — optional grouping. Lets you tag many runs as part of the same investigation; useful for sweeps and ablations.
- **Hypothesis** — free-form notes. Your prediction about what this run should produce. Re-reading the hypothesis when the run completes is how you keep yourself honest about whether the result matched the plan.

### TRAINING tab

The technical tab. The form adapts to SFT vs GRPO.

**Shared fields:**

- **Kind** — SFT or GRPO toggle at the top.
- **Base model** — picker. Two source modes:
  - **HuggingFace** — paste an HF model id (e.g. `Qwen/Qwen3-8B-Instruct`).
  - **Data Hub** — pick from your Hub's Model-kind repos.
- **Precision** — `bf16` / `fp8` / `nvfp4` / `qlora`. `bf16` is the safe default.
- **Batch size, learning rate, sequence length** — the trainer's hyperparameters. Defaults are sensible; see [Precision and recipes](/guides/precision-and-recipes) for the matrix.

**SFT-specific:**

- **Dataset** — picker. Two source modes:
  - **HuggingFace** — pull a dataset directly from HF.
  - **Local** — pick from your Datasets list.

**GRPO-specific:**

- **Environment** — pick from your [RL Environments](./rl-environments.md).
- **Dataset** — the seed dataset bound to the environment.
- **GRPO sub-mode** — see below.

### GRPO sub-modes

GRPO has three flavours that shape how rewards are computed:

| Sub-mode | How reward works | Use when |
|---|---|---|
| **Environment** | The environment itself scores trajectories — pytest pass rates, math correctness, environment-defined predicates. The trainer optimises directly against this numeric reward. | You have a programmatically-verifiable environment (Code + Tests, Math). |
| **Agent** | A separate reward-model **agent** rates trajectories. The trainer optimises against the agent's score. | The environment can't produce a clean numeric reward directly, but you have a strong critic model that can rate outputs. |
| **RULER** | Surogate-specific reward shaping for sparse-reward environments.  | You're training against a sparse environment where most rollouts get zero reward. |

The sub-mode is set on the New Run form when GRPO is selected.

Finally, pick a **GPU offer** from a connected backend. Submit.

## What happens next

<Figure
  src="/img/screenshots/training-detail.png"
  alt="Training Run detail with Logs / Metrics / Artifacts tabs and loss curves visible"
  caption="Run detail — Logs, Metrics, Artifacts. Promote the artifact to a Model when it completes."
/>

The run lands in [Compute → Workload Queue](./compute.mdx) under kind `sft` or `grpo`. The detail panel has four tabs:

- **Logs** — the trainer's stdout/stderr in real time. Verbose; mostly useful for debugging crashes.
- **Metrics** — loss curves, learning rate, throughput, gradient norms, validation metrics. The main tab to watch during a run.
- **Artifacts** — the weights, ready to promote. Empty until the run starts producing checkpoints.
- **Config** — the full resolved configuration. Useful for reproducing the run later, and for diff-ing against other runs.

### What a healthy run looks like

- **Loss** — starts somewhere between 1.5 and 3.0, drops smoothly, plateaus near the end.
- **Throughput** — steady tokens-per-second. Sudden drops usually mean a data-pipeline stall.
- **Gradient norm** — small range, no spikes. Spikes above an order of magnitude precede NaN risk.

### Checkpointing and resume

The trainer writes checkpoints at the configured interval (every N steps, defaults to a recipe-specific value). On crash, a resumed run picks up from the last checkpoint — you don't lose more than the checkpoint interval's worth of work.

For long runs on spot-style compute (Vast.ai, spot AWS), checkpoint frequently — every 500 to 1,000 steps. The cost of writing checkpoints is small; the cost of losing work to preemption is large.

## Promote the result

When the run completes, open its detail and click **Promote to Model** on the Artifacts tab. The dialog opens pre-populated for a Local Hub model deploy; pick backend, GPU offer, replicas, quantization, submit.

Then open your Agent → Settings → swap the Model. Redeploy. Your agent now runs on the model you just trained.

Don't skip the eval step between promote and flip. Run an [Evaluation](./evaluations.mdx) (or an [Arena](./arenas.mdx)) comparing the new model against the old one on your suite before you cut over.

## Cancel a run

From [Compute → Workload Queue](./compute.mdx) filtered to `sft` or `grpo`, open the row menu → **Cancel**. Partial weights are kept; the compute reservation releases.

You can promote a partial run's checkpoint as a Model — useful when an early-stopping decision suggested the run was good enough at step N and didn't need to go to completion.

## Multi-node and distributed

The Surogate Trainer handles distributed training across multiple nodes via Ray. The Ops UI exposes this as advanced fields on the run config:

- **Node count** — how many GPU hosts. Defaults to 1.
- **Devices per node** — how many GPUs per host. Defaults to all available on the chosen offer.
- **Strategy** — `ddp` (data parallel), `fsdp` (sharded), `tensor` (tensor parallel). Most runs use `ddp`; very large models use `fsdp`.

Multi-node runs land as a single row in the Workload Queue but provision N instances. Cancel cancels them all; one node failing fails the whole run.

## Stacked LoRA and MoE

Two specialised patterns the trainer handles:

- **Stacked LoRA** — training a LoRA on top of an existing LoRA adapter. The form has a checkbox for "base is a LoRA-adapted checkpoint"; picking it lets you stack.
- **MoE** — Mixture-of-Experts models with imbalance detection. The trainer monitors expert utilisation and warns when one expert is dominating; useful for catching degenerate MoE configurations early.

Both surface as advanced fields; the math is in the [Trainer docs](/old-docs).

## Compare runs

The Training Runs list supports multi-select. Pick two or more rows; click **Compare**. The comparison view shows:

- The runs' loss curves overlaid.
- The hyperparameter diff (which fields differ across the runs).
- The runs' final eval scores side-by-side (if both have promoted models and shared evals).

Useful for hyperparameter sweeps and for "did this change actually help".

## When this isn't worth doing

- **Fewer than a few hundred clean sessions.** Garbage in, garbage out.
- **The agent's job is genuinely open-ended.** Specialisation helps narrow tasks; it hurts broad ones.
- **You're not paying for inference yet.** Until cost is real, the loop is overkill. Run on a proxied frontier model.
- **You don't have a verifiable reward signal (GRPO).** GRPO on a noisy reward learns the noise. Use SFT or a different paradigm.

## When something fails

- **Stuck in Provisioning.** No GPU available in the chosen backend / region. Loosen the GPU requirement or connect a different backend.
- **Loss diverges.** Most often a too-large learning rate. Cancel, lower by 2-4×, re-run from the latest checkpoint if the trainer supports it.
- **Loss flat at high value.** Learning rate too small, or batch size too large for the model. Lower batch or raise learning rate.
- **Multi-node run hangs at startup.** One node failed to provision; the run waits for the full group. Cancel and resubmit; the scheduler picks different instances.
- **OOM during training.** Sequence length × batch size × precision doesn't fit on the GPU. Lower one of those, or pick a bigger GPU.
- **GRPO reward stays at zero.** The environment isn't producing usable rewards. Inspect a few rollouts in the trajectory viewer; usually the reward function has a bug.
- **MoE imbalance warning.** One expert is getting all the tokens. The trainer auto-rebalances if configured; otherwise reduce the auxiliary loss weight or pick a different MoE recipe.
