# Playground

The Playground is an ad-hoc testing surface for a single Model. No agent wrapper, no skills, no knowledge base — just the bare model behind your Surogate proxy. Use it to sanity-check a model after deploying it, to tune a system prompt before wiring it into an agent, or to compare two models head-to-head without committing to either.

It's the simplest surface in Surogate Ops, and the one builders end up using more than they expect. Every model gets a Playground page; every model gets tested there before any agent ships on it.

## When to use it

Three concrete situations:

- **You deployed a model and want to confirm it responds at all.** First token in under a second, sensible content out — that's the smoke test before you build anything else on top.
- **You're crafting a system prompt and want to iterate.** Each edit in an agent's Settings → Save → redeploy cycle takes seconds; in the Playground it takes none. Iterate here, then paste the final prompt into the agent.
- **You want a quick head-to-head between two model versions.** Open two browser tabs, point each at one model, ask the same question. The cheapest comparison Surogate gives you.

It's not the right tool for production validation — that's what [Evaluations](./evaluations.mdx) is for — and it's not the right tool for skill or KB testing, since neither is reachable from the Playground.

## How to use it

Operate → **Playground**. Pick a model from the dropdown (or arrive via `?modelId=<id>` to land directly on a specific model). Type into the input, adjust sampling parameters, hit send. The response streams back.

The full URL pattern: `/playground?modelId=<model-id>&systemPrompt=<urlencoded>`. The `systemPrompt` query parameter pre-fills the system prompt field — useful for sharing a prompt-under-iteration with a teammate.

## Sampling controls

The right-hand panel exposes the standard sampling parameters. The defaults match the model's own default; you can override per call.

| Parameter | Range | What it does |
|---|---|---|
| **Temperature** | 0 to 2 | Higher = more random / creative. 0 = deterministic (model picks the top token every time). 0.7 is the standard default for chat. |
| **Top-p** | 0 to 1 | Nucleus sampling. Caps sampling to the smallest set of tokens whose cumulative probability is at least *p*. 0.95 is the standard default. |
| **Max tokens** | 1 to model context | Hard cap on the completion length. The model truncates at this limit even mid-sentence. |
| **Stop sequences** | comma-separated | Up to a few sequences that terminate the response. `\n\nUser:` is a common stop for chat-style continuations. |
| **Frequency penalty** | -2 to 2 | Discourages repetition. 0.5 is mildly anti-repetitive; values above 1 distort the output. |
| **Presence penalty** | -2 to 2 | Discourages topic-staying. Pushes the model toward new material as it generates. |

Two practical rules:

1. **Don't tune two parameters at once.** Move temperature, hold everything else; then move top-p, hold everything else. You can't tell which knob did what otherwise.
2. **Reset to defaults between unrelated tests.** It's easy to leave temperature at 0 from a determinism test, then wonder why everything is suddenly terse and stilted.

## System prompt iteration

The Playground's biggest payoff is the system-prompt iteration loop. Type a system prompt, ask the agent's most common question, read the response, edit the prompt, re-send. Each cycle is seconds.

The pattern that works:

1. **Start blunt.** "You are a helpful assistant" tells you what the bare model does. Read the response.
2. **Constrain.** Add the constraints that matter for your use case — tone, format, what to refuse, what to always include.
3. **Test the edge cases.** Once the typical case looks right, ask the edge cases that broke previous prompts. Did this prompt break them too?
4. **Read the failures.** When the response is wrong, the system prompt almost always tells you why.
5. **Paste the final prompt into the agent's Settings → System prompt** and redeploy.

Twenty minutes in the Playground saves an afternoon of agent redeploys.

## Differences from agent chat

The Playground is bare model. An agent is bare model + system prompt + skills + KB + session history. Several practical consequences:

- **No skills, no KB.** The model gets only what you type. Use this to isolate "is it the model, or is it the wrapping?" If the model handles a question fine in the Playground but the agent fails it, the failure is in the skills / KB / prompt.
- **Ephemeral sessions.** Playground sessions aren't stored under [Sessions](./sessions.mdx). Useful for quick iteration; not useful for audit. If you want a Playground response saved, copy it out.
- **No session history.** Each prompt starts fresh. The chat-style UI shows the conversation, but the model only sees the messages you've sent in this window — there's no persistent memory between visits.
- **Token usage counts.** What you do here counts toward the chosen model's usage on the cloud backend. A long Playground iteration on a proxied frontier model can run up a noticeable bill.

## Comparing two models

The Playground is the right tool for a quick A/B test. Two patterns:

### Side-by-side tabs

Open two browser tabs:

1. Tab A → Playground → pick model A.
2. Tab B → Playground → pick model B.
3. Ask the same prompt in both. Watch the responses stream side-by-side.

Fast, free, no setup. Good for "is the new model worse on my prototypical question?".

### Same window, swap models

Pick model A, ask the prompt, save the response. Pick model B from the dropdown — the chat clears — ask the same prompt. Compare manually.

Less ergonomic but lets you use the back/forward controls to flip between responses.

For a *real* comparison — significance-tested, sample-counted, scored — use [Evaluations](./evaluations.mdx). The Playground is for the qualitative "which one *feels* right" judgement that precedes the rigorous test.

## Common testing patterns

A handful of small recipes that pay off:

- **Smoke test after every model deploy.** Two seconds, prove the model responds.
- **Determinism check (temperature = 0)** — call the same prompt twice; the responses should match exactly. If they don't, something below the model is non-deterministic (a tool injection, a system-prompt rotation, a caching issue).
- **Refusal probe.** Try a query that should trigger refusal. Confirm the model refuses cleanly. Refusal quality is genuinely model-dependent; the Playground is the cheapest way to test it.
- **Verbosity check.** Long-form prompts ("explain in detail…") on a model meant for short answers will go off the rails before they go silent. Test before you ship.

## Antipatterns

A handful of recipes that don't work, that builders often try anyway:

- **Treating Playground results as production-grade evidence.** They aren't. Use [Evaluations](./evaluations.mdx) for that.
- **Stress-testing concurrency from the Playground.** Each Playground call is one user, one stream. For concurrent-load testing, hit the [Inference API](../api/inference.md) directly with a load generator.
- **Testing skills here.** You can't. Skills live in agents, not in the Playground.
- **Using the Playground to share prompts with the team.** The URL `?systemPrompt=...` works but is fragile. For team-shared prompts, paste into a Skill body or a project doc.

## When this isn't the right surface

- **You need to test a skill.** Go to the agent in Studio, attach the skill, run sessions.
- **You need to test a KB.** Same — attach in the agent's Settings and run sessions.
- **You need a multi-turn conversation.** The Playground supports chat-style continuation in a window, but there's no persistence; closing the tab loses the conversation. For multi-turn iteration tied to an agent, use a Sessions-backed run.

## When something fails

- **No models in the dropdown.** None of your models is in **Serving** status. Open [Models](./models.mdx), deploy or restart one.
- **Stream starts then drops mid-response.** Network blip between your browser and the inference proxy, or a transient model error. Re-send; the issue usually clears.
- **First token takes more than a few seconds.** Model is cold (a Modal-style serverless backend hasn't warmed up) or undersized for the request. The second call is usually fast; if not, pick a bigger GPU.
- **Response is empty.** The model produced a single stop token at position 0. Usually a system-prompt issue — you've told the model to refuse, or your stop sequences are too eager.
- **`401 invalid_key`** in the response. Your in-app session expired. Sign out and back in.
