# Compute

Compute is what ties Surogate Ops to actual machines. Serving containers, training runs, eval jobs, synthetic-data pipelines — every workload draws from the cloud accounts you connect here.

The Compute page has three sub-views: **Cloud** (connected backends), **Workload Queue** (running and queued jobs), and **Policies** (allocation rules).

## Connect a cloud backend

Compute → **Cloud** → click a provider tile (or **Connect Cloud**). Eight providers are supported: AWS, Azure, GCP, RunPod, Modal, Nebius, OCI, Vast.ai.

Each provider's credential form differs. The full per-provider list:

| Provider | Fields |
|---|---|
| **AWS** | Access Key ID, Secret Access Key |
| **Azure** | Tenant ID, Subscription ID, Client ID, Client Secret |
| **GCP** | Project ID, Service Account Key (JSON, paste or browse) |
| **RunPod** | API Key |
| **Modal** | Token ID, Token Secret, Environment |
| **Nebius** | Service Account ID, Public Key ID, Private key (.pem upload) |
| **OCI** | User OCID, Tenancy OCID, Fingerprint, Home Region, Private Key (.pem upload) |
| **Vast.ai** | API Key |

Each form has a deep-link to the provider's own console (AWS Console, Azure Portal, etc.) for finding the values. Submit. The form returns to Cloud with the new backend marked **Connected**.

**Verify it worked.** Click into the backend; the **Offers** panel should list GPU types your account is eligible for, with current price per hour. Empty offers usually means missing IAM read on instance-type metadata, or no GPU quota in the queried regions. See the per-backend page ([AWS](../compute-providers/aws.md), [Azure](../compute-providers/azure.md), [GCP](../compute-providers/gcp.md), etc.) for the troubleshooting flow.

For deep setup steps per backend — IAM users, service accounts, regions, supported instance types — see the [Compute providers folder](../compute-providers/aws.md).

## Workload Queue

<Figure
  src="/img/screenshots/compute-workload-queue.png"
  alt="Workload Queue showing the kind filter pills (all / sft / grpo / serving / eval / task / synthetic) and a row table with Pri, Workload, Type, Status, GPU, Location, Progress, Requested By"
  caption="Workload Queue — every running and queued job. Filter pills carry live counts per kind."
/>

Train runs, eval jobs, serving containers, synthetic generators — they all land here.

### The seven workload kinds

Filter pills at the top: `all · sft · grpo · serving · eval · task · synthetic`. Each pill shows a live count.

| Kind | Originates from | What it does |
|---|---|---|
| **sft** | New Training Run → SFT | Supervised fine-tuning. Long-running; checkpoints as it goes. |
| **grpo** | New Training Run → GRPO | RL training. Long-running. |
| **serving** | Deploy Model | Hosts a model's serving container. Long-lived; one per model replica. |
| **eval** | New Evaluation | Scores a model against a benchmark. Short to medium runtime. |
| **task** | KB compile, dataset transform, generic scheduled jobs | Short-running operational work. |
| **synthetic** | New Dataset → Synthetic Generation | Produces synthetic training examples. |
| *(Arena workloads inherit the kind of their underlying sub-job — `eval` for round evals, `sft`/`grpo` for sub-training)* | | |

### Column schema

| Column | Meaning |
|---|---|
| **Pri** | Priority. Higher priority workloads jump the queue when capacity opens. |
| **Workload** | The name (run name for sft/grpo, agent slug for serving, eval suite for eval, etc.). Click to drill in. |
| **Type** | The workload kind. |
| **Status** | Current lifecycle state — see below. |
| **GPU** | The GPU offer the workload is targeting. |
| **Location** | The backend and region the workload is running in. |
| **Progress / ETA** | Live progress bar or estimated time remaining. |
| **Requested By** | The user who submitted the workload. |

A trailing row-actions menu offers:

- **Cancel** — stops the workload immediately. Partial work (checkpoints, generated rows) is preserved.
- **View logs** — opens the workload's log stream.
- **Re-run** — clones the workload as a new submission with the same config.

### Status state machine

`Queued → Provisioning → Running → Completed / Failed / Cancelled`

- **Queued** — accepted, waiting for a backend with capacity to claim it.
- **Provisioning** — backend is bringing the instance up.
- **Running** — work in progress.
- **Completed** — finished successfully.
- **Failed** — finished with a terminal error. The detail's logs show the cause.
- **Cancelled** — operator cancelled.

A workload can also enter **Error** before queuing if a Compute Policy refuses it — see Policies below.

## Backend offers

Each connected backend has a per-backend detail page with an **Offers** panel listing every GPU type your account is eligible for. Columns:

- **GPU type** — A100, H100, L4, etc.
- **GPU count** — single-GPU vs multi-GPU instances.
- **Region** — where the offer is available.
- **Price per hour** — current on-demand price.
- **Spot price** (where applicable) — current spot price.
- **Bandwidth** (for Vast.ai-style heterogeneous backends) — network bandwidth of the host.

The offers list is live — refreshed every few minutes. When you submit a workload, the scheduler picks an offer that matches the workload's GPU requirement, the Compute Policy's constraints, and current availability.

## Policies

<Figure
  src="/img/screenshots/compute-policies.png"
  alt="Compute → Policies tab listing existing policies with Edit actions and the + New Policy button in the top-right"
  caption="Compute → Policies — allocation rules. + New Policy opens the editor (admin-only)."
/>

A Policy bounds where workloads can run. Policies are evaluated before a workload is scheduled; violations land the workload in **Error** with a Guardrail alert and never enter the queue.

Compute → Policies → **+ New Policy** opens the editor. The action is admin-only — non-admins see the button but clicking it is a no-op.

### Policy fields

- **Name** — human-readable. Shows up in alerts.
- **Allowed backends** — multi-select. A workload that requests a backend not in this list is refused.
- **Allowed regions** — per-backend allowed regions.
- **Allowed instance types** — per-backend allowed GPU families.
- **Spend caps** — monthly USD ceiling per backend, plus an alert-at threshold (defaults to 80%).
- **Schedule windows** — optional. Only allow workloads during specified hours / days.
- **Applies to** — scope: install-wide, per-project, per-team, per-user.

Multiple policies can match a workload; the workload must pass *all* of them.

### When policies are the right tool

- **Capping a runaway training spend.** Set a cap; the platform refuses workloads that would cross it.
- **Restricting expensive instance types** to admins or to specific projects.
- **Region pinning** for data-residency.
- **Off-hours scheduling** — only let big training runs start after business hours.

### When they aren't

- **Per-call rate limiting.** Use the inference proxy's rate limits ([Errors and rate limits](../api/errors-and-rate-limits.md)) instead.
- **Workload prioritisation.** The Priority field on the workload is the right tool; policies are about *what's allowed*, not *what runs first*.

## Monitoring

The dashboard's **Training Jobs** and **Serving Models** tiles show the current count. The Workload Queue's filter pills carry live counts per kind. Per-backend usage is on each backend's detail page.

For deeper monitoring, the platform emits Prometheus metrics ([Self-host → Monitoring](../deployment/self-host.md#monitoring)) that you scrape into your own Grafana.

## Connect-and-go: a workflow

A reasonable order to bring a new install up to compute parity:

1. Connect one easy backend (RunPod or Vast.ai) for fast experimentation.
2. Connect one hyperscaler (AWS or GCP) for production serving.
3. Set a default Compute Policy capping monthly spend per backend.
4. (Optional) Add Modal or Nebius for backend-specific advantages.
5. Test a workload of each kind (deploy a small model, run a tiny eval, do a one-step training run) to confirm the path is healthy.

## When something fails

- **A connected backend lists zero offers.** Credentials are valid but the IAM role lacks instance-type metadata read, or the account has no GPU quota in the regions Surogate queries. See the per-backend page.
- **Workload stays Queued forever.** No backend has capacity for the requested GPU. Loosen the GPU requirement, broaden the region set, or connect a provider with stock.
- **Workload fails to provision.** Open the row menu → View logs. Most often a transient provider error; retry usually clears it.
- **Policy refuses every workload.** The policy is over-restrictive. Loosen the allowed instance types or regions.
- **Spend cap alert at 80%** of the policy's monthly budget. Open the policy; either raise the cap, or audit which workloads are consuming it.
- **A serving workload runs hot CPU and degraded throughput.** The instance is undersized for the model. Stop, redeploy on a bigger offer.
- **Backend tile shows Connected but the offers list keeps re-querying.** Transient API rate-limiting from the upstream provider. Wait a minute; if it persists, the credential is failing silently on a specific permission.
