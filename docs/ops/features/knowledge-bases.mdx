# Knowledge Bases

A Knowledge Base (KB) is an indexed document store that agents read at runtime. You point it at a source — your help center, your wiki, a folder of PDFs — and Surogate compiles it into a pair of indices that agents query during conversations to ground their answers in your content.

Unlike a plain RAG setup, Surogate's KBs aren't just embedding indices — they're curator-mediated. A curator model runs after every ingest and writes structured artifacts that retrieval reads from. The architecture is in [Concepts → Architecture](../concepts/architecture.md).

## When to use a KB

- Your agent should answer from your own docs, not from whatever the model learned in pretraining.
- The source content changes — a wiki, a help center, a product spec — and you want answers to track edits.
- You need retrieval calls to be visible: opening a session shows which documents the agent pulled from, which makes debugging answers tractable.
- You need citation-grounded answers that point back at the source document.

## Create one

<Figure
  src="/img/screenshots/kb-new-dialog.png"
  alt="New Knowledge Base dialog with Display Name, Slug, Description, and Source picker"
  caption="New Knowledge Base — the four-field dialog. Source picker decides where the documents come from."
/>

Build → Knowledge Bases → **+ New Knowledge Base**. Fill four fields:

- **Display Name** — what users see in lists and on agent settings.
- **Slug** — permanent identifier; can't be changed later.
- **Description** *(optional)* — shown on the KB card.
- **Source** — pick where the documents come from (see Sources below).

Submit. The KB lands in **Compiling** while Surogate fetches and embeds the source. When the compile finishes it flips to **Active** and is attachable to agents.

A compile workload appears in [Compute → Workload Queue](./compute.mdx) with kind `task`. Big sources (thousands of documents) can take minutes to compile.

## The Sources tab

The KB detail has a **Sources** tab listing every source attached. A KB can have one source or many; many KBs end up with a couple — your help centre URL plus a folder of internal PDFs, say.

The five source types:

### File upload

Drag a folder of files (`.md`, `.pdf`, `.txt`, `.html`, `.docx`) into the dropzone. The files upload to the KB's storage and become a source.

Use for: handbooks, contracts, anything you maintain as files.

### URL

Paste a URL. Surogate crawls the page (and, by default, linked pages within the same origin). Crawl depth is configurable per source.

Use for: help centres, public documentation sites, any web-published content.

### Git

Point at a Git repo (HTTPS clone URL). Surogate clones the repo, indexes the named subpath, and re-pulls on the configured schedule.

Use for: docs-as-code workflows where your team edits Markdown in a repo.

### S3

Point at an S3 bucket with optional prefix. Surogate lists the bucket, downloads matching files, and re-syncs on the configured schedule.

Use for: large document corpora that already live in object storage.

### Existing Hub repo

Pick a Dataset-kind Hub repo. The KB reads from the repo's contents.

Use for: KBs you want versioned and sharable across projects.

Each source has its own settings: credentials, schedule, crawl depth (URL), include / exclude globs (Git, S3).

## The Curator tab

The KB detail's **Curator** tab is where the structured artifacts get configured.

Surogate ships a **default Surogate curator** — a model fine-tuned for the curator task. It runs after every ingest and produces:

- A **per-source wiki**: one structured document per source, organised hierarchically. Captures the document's content in a form optimised for retrieval.
- A **cross-source synthesis index**: links related material across sources. Lets the agent pull from multiple sources when the answer requires synthesis.

Both indices live on the KB and are read at retrieval time.

The default curator works for most teams. Two things you can change:

- **Swap the curator model.** Pick a different model from the dropdown (any Serving model). Useful when the default doesn't extract the right structure for your domain.
- **Edit the system prompt.** The default prompt is shown in an editable text area. Customise to bias what the curator extracts — for example, *"prioritise extracting product feature names, version numbers, and known issues."*

After editing the system prompt or swapping the model, re-ingest the KB to regenerate both indices.

## Attach to an agent

<Figure
  src="/img/screenshots/kb-attach-to-agent.png"
  alt="Agent Settings tab with Knowledge bases multi-select expanded showing several KB options"
  caption="Attaching KBs from the agent's Settings tab. Multi-select; the agent decides which to query per turn."
/>

Open the agent → **Settings** → **Knowledge bases** multi-select → redeploy. Multi-select means an agent can read from several KBs at once; the agent decides which to query for each turn based on the question and the KB descriptions.

A KB in **Compiling** or **Error** state can be attached. The agent returns no retrieval results until the KB reaches **Active**.

Multiple agents can attach the same KB. There's no per-agent KB copy; the agents share the underlying index. This is what makes "attach our help centre KB to every customer-facing agent" cheap.

## Re-indexing

Saving a KB triggers re-index. While the new index builds, the agent keeps hitting the previous index — there's no read-time gap. The new index swaps in atomically when the compile completes.

For sources that change frequently (a wiki on a daily edit cadence), set the compile to run on a schedule rather than re-saving by hand. Schedule options on each source:

- **Manual only** — only when you save.
- **Hourly** — every hour.
- **Daily** — at a specified time.
- **Weekly** — on a specified day and time.

Multi-source KBs run independent schedules per source; the cross-source synthesis re-runs when any source completes.

## Retrieval at runtime

When an agent queries the KB during a session, the trace shows:

1. **The retrieval call** — the agent's reformulation of the user's question, the KBs queried.
2. **The candidate documents** — top-k matches from the per-source wiki and the synthesis index, each with a relevance score.
3. **The injection** — how the candidate documents got merged into the prompt the model saw.

This visibility is the diagnosis surface. "The agent gave a wrong answer" usually traces back to one of:

- The retrieval returned the wrong documents (the user's question didn't reformulate well; the index is missing the topic).
- The retrieval returned the right documents but the injection truncated them (long documents, tight context budget).
- The retrieval returned the right documents and the model ignored them (system prompt isn't strong enough on grounding).

Open a session, read the retrieval step, and you know which.

## Status

| Status | Meaning |
|---|---|
| **Compiling** | Surogate is pulling the source and building the curator's indices. |
| **Active** | Indices ready; queries return results. |
| **Error** | A document fetch or the indexing step failed. Open the KB to see per-document errors. |

## When this isn't worth doing

- **Your agent answers purely from instructions, not from content.** A KB is overhead if there's nothing for it to retrieve. Use the system prompt directly.
- **The content fits in the prompt.** A few hundred words of context belongs in the system prompt, not in an indexed KB. The KB pays off when the corpus is larger than the context window or when it changes independently of the agent.
- **The agent doesn't need citations.** If "this is on our help site" is enough for the user, point them at the help site rather than building a KB.

## When something fails

- **Stuck in Compiling longer than expected.** Open [Compute → Workload Queue](./compute.mdx) and filter to `task`. Find the related job. If **Queued**, no compute is available. If **Failed**, click the row for logs.
- **Active but retrieval returns nothing.** Two possibilities. Either the agent isn't pinned to this KB version (redeploy), or your query is outside the KB's embedding distribution (the topic is genuinely not in the source). Open a session and look at the retrieval step to confirm.
- **Error with a 401/403 source.** A source credential expired upstream. Re-enter in the source's settings.
- **Retrieval returns the wrong documents.** The curator's extraction isn't optimal for your domain. Edit the curator system prompt; re-ingest.
- **Re-index ran but the agent still serves old answers.** The agent is pinned to a previous KB version. Redeploy the agent.
- **One source is healthy, another is in Error.** Each source has its own ingest state. The healthy one keeps serving; fix the broken one separately.
