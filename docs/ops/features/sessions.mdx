# Sessions

A Session is one chat thread between a user and an agent. Sessions live in two places — the Work side shows your own sessions, the Studio side shows every session you can see across the projects you're a member of.

Sessions are the operational heart of Surogate Ops. Every other surface — datasets, training, evaluations — eventually reads from here.

## When to open a session

- **A user reports a bad answer.** Open the session to see what the agent actually said and why.
- **After a deploy.** Sample-check that the new version of the agent behaves the way you intended.
- **To flag good and bad sessions** for the next training dataset.
- **To audit a sensitive interaction.** Compliance, support escalation, anything you'll need to reconstruct later.

## The three filter dimensions

The Sessions list filters along three orthogonal axes; combine them freely.

### Status

| Status | Meaning |
|---|---|
| **All** | Default. Every session regardless of state. |
| **Active** | The conversation is still in progress — the user has the chat open, or the agent's last response hasn't returned yet. |
| **Completed** | The conversation ended cleanly. Most sessions end up here. |
| **Failed** | The agent hit a terminal error mid-conversation. Usually a skill failure or an upstream model error. |
| **Archived** | Sessions an operator moved out of the active list. Still queryable, still readable, just out of the way. |

### Events

Cross-cutting event filters. A session matches if any message in its trace fired the named event.

| Event | When it fires |
|---|---|
| **Denied** | The agent or the platform refused a request — content guardrail, policy gate, scope check. |
| **Overridden** | An operator overrode a Coordinator or Steering decision (typically inside an arena participant). |
| **Crashed** | The agent's process crashed mid-call. Distinct from Failed (which is a controlled terminal state) — Crashed is uncontrolled. |

### Sentiment

| Sentiment | Source |
|---|---|
| **👍** | End user thumbs-upped a message, or a reviewer flagged the session as good. |
| **👎** | End user thumbs-downed a message, or a reviewer flagged the session as bad. |

Each filter pill carries a live count. The combination "All sessions, no event filter, sentiment 👎" is the most-used filter — it's the daily "what went wrong yesterday" view.

## What a session shows

<Figure
  src="/img/screenshots/session-detail.png"
  alt="Single Session detail page showing the message thread alongside the agent's reasoning, skill invocations, and KB retrieval calls"
  caption="Session detail — every model call, skill invocation, and retrieval call rendered alongside the chat thread."
/>

Opening a session in Studio reveals the agent's full step-by-step run, not just the messages:

- **Every user message** the conversation contained.
- **Every model call** with the assembled prompt (system + user history + any injected context) and the streaming response tokens.
- **Every skill invocation**, with the arguments passed in and the return value.
- **Every retrieval call** against a knowledge base, with the documents pulled and the relevance scores.
- **Every error** along the way — skill timeouts, KB compile-state issues, upstream model failures.
- **Every steering or guardrail event** the platform emitted.

This is where you debug. "Why did the agent say X?" is answered by reading backwards from X to the prompt that produced it.

The trace is on the right side of the detail by default; some teams prefer the messages-only view, which is available via the layout toggle in the toolbar.

## Flag a session

<Figure
  src="/img/screenshots/session-flag-controls.png"
  alt="Session row with the 👍 / 👎 sentiment buttons and the flag chip in the right-hand action column"
  caption="Flag and sentiment controls on a session row. Flagged sessions feed the next training dataset."
/>

Sessions can be flagged for review. Flagging works at two granularities:

- **Per-message flag** — 👍 or 👎 on a single message. End users do this; you also do it as a reviewer.
- **Session-level flag** — flag the whole session as good or bad. Use when the issue isn't tied to one message (e.g., the whole conversation was off-topic).

Flagged sessions form the pool you later turn into a training dataset via [Datasets → From Conversations](./datasets.mdx). Flag liberally — quality matters more than quantity for training, and a quarterly review of flagged sessions is the cleanest signal you'll have about what's working.

**A flag is reversible.** If you click 👎 by accident, click it again to clear, or click 👍 to flip.

## Session URLs and deep links

Every session has a stable URL: `/work/<agent-slug>/sessions/<session-id>` for end users and `/studio/sessions/<session-id>` for builders. Both URLs are durable — bookmark them, paste them into Slack, link them from a ticket.

End-user URLs let anyone with the link pick up the chat where it left off (assuming they have project access). Builder URLs land on the trace view; they're what you paste into a debugging thread.

Two practical patterns:

- **In a Slack hand-off**, paste the builder URL. The receiver lands on the trace immediately.
- **In a Linear / Jira ticket**, paste both URLs. The end-user URL is what QA reproduces against; the builder URL is what an engineer debugs from.

## Search

The top-right search box queries across session content — user messages and agent responses. Two qualifier prefixes narrow the search:

- `agent:<slug>` — only sessions on the named agent.
- `flag:<good|bad>` — only flagged sessions of the chosen polarity.

Combine: `agent:support-bot flag:bad refund` finds every 👎-flagged session on the support bot that mentioned refunds.

The search is full-text; substring matches, no fuzzy matching. For semantic search across sessions, run the search prompt through an agent backed by a KB built on session exports.

## Export a session

Session detail → row menu → **Export**. Downloads a JSON bundle containing:

- The full message thread.
- The complete trace (model calls, skill invocations, retrieval calls).
- All metadata (timestamps, agent version, model version, flag state).

Use this for:

- **Sharing a session with someone outside Studio access.**
- **Diff-ing two sessions** — same prompt, two model versions, where exactly did they diverge?
- **Building a custom analysis** in a notebook.

The JSON shape is stable across releases; treat it as a public format.

## Retention and archival

Two related but distinct concepts.

- **Archival** is a soft move. Archived sessions stay queryable through the **Archived** status filter; they just don't show up in the default list. Use for sessions you don't need to see daily but want to keep accessible.
- **Retention** is the platform-level lifecycle. Sessions are kept after the agent that produced them is deleted — they drop into a read-only state but remain queryable for audit. The install-level retention window defaults to indefinite; admins set a window in **Settings → Audit log** if compliance requires one.

There is no per-session "delete" — sessions are an auditable record, and the platform treats them that way. The closest you get is archival.

## Retention vs personal data

If a session contains PII you can't legally retain, the path is:

1. **Archive the session.** Removes it from the default view.
2. **File a data-deletion request** through Settings → Audit log → Data deletion.
3. The request is reviewed and the session is purged on the install's data-deletion cadence (typically nightly).

Don't paste PII into a chat as a test case — by the time you regret it, the trace is captured.

## When this isn't worth opening

- **You already know the answer.** A glance at the dashboard told you the agent's RPS spiked; you don't need to read individual sessions to know there's load.
- **The session is from a closed agent you've already replaced.** Read the trace for posterity if you like, but don't iterate on it — the new agent's traces are what to look at.
- **You're doing aggregate analysis.** Export many sessions, do the analysis in a notebook; reading them one by one in Studio is the slow path.

## When something fails

- **Session shows status Active but the user closed the chat hours ago.** Sessions don't auto-close on user disconnect. Wait for the install's idle-timeout cron, or archive manually.
- **Trace shows a skill call that returned but the response doesn't reflect it.** The model decided to ignore the skill's return value — usually a description-prompt mismatch. Read the assembled prompt to see how the return value was injected.
- **A 👎 flag isn't showing up in the dataset.** The dataset's quality filter is excluding it. Confirm the **From Conversations** filter matches the flag state (👍 only, 👎 only, or all-flagged).
- **Export downloads a file with no trace, just messages.** Your project role is Viewer; traces are gated on Editor or Owner. Ask the project owner to bump your role.
- **Stuck loading the detail page.** Very large sessions (hundreds of messages, thousands of trace entries) can stall the render. Refresh; if it persists, export and read locally.
