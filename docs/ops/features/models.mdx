# Models

A Model is the LLM your agents call. Surogate Ops either serves it for you on your connected cloud compute, or proxies it to an upstream provider. Either way your agents reference the model by id, and external callers can reach it through Surogate's [Inference API](../api/inference.md).

The Models page is the inventory of every model your install can route traffic to — served or proxied, healthy or otherwise.

## The four sources

<Figure
  src="/img/screenshots/models-source-picker.png"
  alt="Add Model dialog showing the four source cards: Local Hub, Hugging Face, OpenRouter, URL"
  caption="Add Model — the source picker. Each card opens a source-specific form on the next screen."
/>

Models page → **Deploy Model**. The dialog opens to a source picker. Each source has its own follow-up form.

### Local Hub

Pull weights from a Hub repo. The default option, and what you use to serve a model your team has trained.

The form asks for:

- **Repository** — autocomplete against your Hub's Model-kind repos.
- **Branch or tag** — defaults to `main`. Pin to a tag for reproducibility.
- **Backend** — which connected cloud the serving container runs on.
- **GPU offer** — drawn from the backend's offers list.
- **Replicas** — how many serving copies. Defaults to 1.
- **Quantization** — `bf16` / `fp8` / `nvfp4` / `qfp4` / `qfp8` / `qlora`. See [Quantization](#quantization) below.

### 🤗 Hugging Face

Pulls weights directly from Hugging Face. The form asks for a model id (e.g., `meta-llama/Llama-3.1-8B`) plus the same backend / GPU / replicas / quantization config as Local Hub.

Gated repos require a Hugging Face token. Set the token in Settings → Integrations once; subsequent deploys reuse it.

### OpenRouter

Proxied through OpenRouter's catalog. Surogate doesn't pull weights — it forwards calls to OpenRouter's API and bills against your OpenRouter credit.

The form is short: pick the OpenRouter model from a dropdown of their catalog, point at an OpenRouter credential in your [Credential Vault](../admin/credential-vault.md).

Proxied models go straight to **Serving** — there's no container to wait on.

### URL

Any OpenAI-compatible endpoint. Paste a base URL and a credential id. Works with self-hosted vLLM, Ollama, internal inference services your team already runs, or another Surogate install's inference proxy.

The form asks for:

- **Base URL** — the OpenAI-compatible host (e.g., `https://vllm.your-vpc:8000`).
- **Model id** — the model name the upstream expects in the request body.
- **Credential** — Vault reference for the upstream API key (if any).

URL-source models are proxied — no container to manage on Surogate's side.

Submit. Served models land in **Deploying** while the container comes up; proxied models go straight to **Serving**.

## Status

| Status | Meaning |
|---|---|
| **Deploying** | Container being built and scheduled. Normal during first deploy. |
| **Serving** | Healthy, accepting traffic from agents and the Playground. |
| **Stopped** | You manually stopped it. Re-deploy to serve again. |
| **Error** | Container or upstream provider returning failures. |

A Model that flips from Serving to Error invalidates every agent calling it. Agents transition to Error themselves until the model is back.

## Replicas and scaling

Served models run with one or more replicas. Each replica is an independent serving container; the inference proxy load-balances requests across them.

Two practical rules:

- **Start with one replica.** Most agents handle their early traffic on a single replica with room to spare. Adding a second is a real cost; don't pre-provision.
- **Add replicas when P99 latency climbs.** The dashboard's agent metrics table shows P99 per agent. When the model serving the agent is the bottleneck (and not a slow skill or KB), bump replicas.

Scaling is manual today. The platform doesn't autoscale; you set the replica count and it stays at that count.

## API keys

<Figure
  src="/img/screenshots/model-api-keys.png"
  alt="Model detail page with the API keys panel showing the create key button and a masked key listing"
  caption="API keys panel on a Model detail page. Keys are scoped to one model; create new before revoking old."
/>

Each model can have one or more API keys for external callers. A key is scoped to that one model — your own services, third-party tools, anything outside Surogate Ops uses it to hit the model through Surogate's [Inference API](../api/inference.md). Agents built on the model don't need a key; they call internally.

The Model detail's API keys panel lists every key with its name, last-used timestamp, and an action menu (Rotate, Revoke). Creating a key shows the value once.

Failed authentications are negative-cached briefly to protect the upstream. A wrong key keeps failing for up to about a minute after the fix.

:::warning Rotation order
Create the new key first, point clients at it, **then** revoke the old. Never delete first — your callers will see authentication failures for the full negative-cache window.
:::

## Quantization

Served models accept several quantization options: `bf16`, `fp8`, `nvfp4`, `qfp4`, `qfp8`, `qlora`. The matrix of legal pairs depends on the GPU. The Surogate Trainer's [Precision and recipes](/guides/precision-and-recipes) guide has the full matrix.

:::tip Default
Pick `bf16` if you're unsure — it's the safe quality default. Pick `qlora` if you're optimising for GPU hours and willing to accept a small quality hit.
:::

The high-precision options (`bf16`) prioritise model quality; the quantized options (`qlora`, `qfp4`) prioritise serving cost. The intermediate ones (`fp8`, `nvfp4`) are reasonable trade-offs on hardware that natively supports them — H100s for FP8, Blackwell-generation for NVFP4.

## Cost shape

Served models reserve compute for the lifetime of the container. Stopping releases the reservation immediately. Proxied models cost nothing on Surogate's side; you pay the upstream provider directly.

The Studio dashboard's Serving Models and Training Jobs tiles show coarse spend. For per-model details, use your cloud backend's own billing.

Practical pointers:

- **Steady-state traffic favours self-served**, especially after you've trained your own expert.
- **Bursty traffic favours proxied**, because you're not paying for idle GPU.
- **Stopping a served model** is the right move when traffic genuinely paused. Re-deploying later is fast because the image and weights cache.

## Update a model

For Local Hub source, "updating" means pointing the same model record at a new commit on the source repo:

1. Push the new weights to the Hub repo (or finish a training run that publishes to it).
2. Models page → row menu → **Update from source**.
3. The serving container redeploys against the new commit. The first call after the swap pays a cold-start; subsequent calls are warm.

Agents pinned to this model see the update automatically — the model id stays the same, but the underlying weights change. If you need to A/B test, deploy the new weights as a separate model with a different id, then swap the agent's model field.

## Stop or delete a model

- **Stop** — releases the serving container immediately. The model record stays; redeploy from the same row to bring it back.
- **Delete** — removes the record entirely. Agents that referenced it go to **Error**. Use only when you're certain no agent depends on this model.

The platform refuses delete if any agent currently has this model attached. Detach the agents (swap them to another model) before deleting.

## When this isn't worth deploying

- **You only need a one-shot test.** Use the [Playground](./playground.mdx) against an existing model rather than deploying a new one.
- **The model isn't trained yet.** Run the [Training](./training.mdx) first; the resulting Hub artifact is what you'd deploy.
- **Traffic is too sparse to justify reserving a container.** Proxy the model through OpenRouter or another hosted provider; pay only for the calls you make.

## When something fails

- **Stuck in Deploying.** Find the related `serving` workload at [Compute → Workload Queue](./compute.mdx) filtered to `serving`. Open the row for logs.
- **API call returns "API key not scoped for this model".** The key was created for a different model. Create a new key on this model.
- **Quantization choice rejected.** GPU type doesn't support that quantization. Pick a different GPU or a different quantization.
- **First-token latency spiked.** Container scaled to zero (only happens on Modal-style serverless backends). Subsequent calls warm; sustained spikes suggest the GPU is undersized.
- **`502 upstream_error`** on proxied calls. The upstream provider returned a failure. Surogate forwards the failure; the root cause is on the upstream side. Check the provider's status page.
- **Model healthy in Playground but agents error.** A skill or KB the agent depends on is unhealthy. Open the agent; the error message names the dependency.
