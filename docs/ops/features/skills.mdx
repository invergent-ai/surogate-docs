# Skills & Tools

Skills are how your agents do work outside of generating text. Read a database, write to a ticket tracker, call an API, run a saved workflow. A skill is a small, typed function with a description; the agent picks when to call it based on the conversation.

**MCP Servers** are the externally-hosted alternative. If a vendor (or another team) already exposes a Model Context Protocol endpoint, you register the URL and the agent can call any tool the server offers. You don't host anything.

The Skills & Tools page has two tabs: **Skills** (the ones your team authored or imported) and **MCP Servers** (the registered external endpoints).

## When to write a skill vs use an MCP server

| You have… | Use |
|---|---|
| A narrow function ("get_customer", "create_ticket") | **Skill** — fast to write, type-safe, stays in Surogate Ops. |
| A vendor that already exposes an MCP endpoint | **MCP Server** — register once, use everywhere. |
| An internal service you'd like to expose to multiple agents | **MCP Server** — host one and connect to it from every agent. |
| A long-running workflow with many steps | **Expert skill** — see below. |

## Write a skill

<Figure
  src="/img/screenshots/skill-builder.png"
  alt="Skill Builder inline editor showing the five top-level fields (Name, Display Name, Description, Trigger, Tags) and the markdown body editor with formatting toolbar"
  caption="Skill Builder — five header fields plus a markdown body. Body editor supports bold, italic, code blocks, and a live-preview toggle."
/>

Build → Skills & Tools → **New Skill**. The Skill Builder opens inline.

### The five header fields

- **Name** — internal id, URL-safe, referenced from agent configs. Permanent.
- **Display Name** — what users see in lists.
- **Description** — what the skill does, in one or two sentences. **Agents read this to decide when to call.** Be precise. A vague description means the agent calls the skill at the wrong times or doesn't call it when it should.
- **Trigger** — optional natural-language hint ("when the user asks about pricing"). The trigger doesn't gate calls — the description still has to be accurate — but it nudges the agent toward the skill when the trigger phrase appears.
- **Tags** — space-separated, used by the filter on the Skills list.

### The IS EXPERT toggle

Below the header fields, an **IS EXPERT** toggle. When enabled, the skill is backed by a deployed model that the base LLM delegates to.

The difference:

- **Regular skill** — a typed function. The base LLM calls it, gets a return value, continues.
- **Expert skill** — a separate model the base LLM hands off to. Useful when the skill's work is itself an LLM task too complex for one-shot reasoning — code review, multi-step planning, domain-specific drafting.

The expert skill's model is configured on the toggle's expanded panel: pick a model, give it a system prompt, optionally restrict the tools it can use. The base LLM treats the expert as a function: input goes in, output comes back. The expert's reasoning is visible in the session trace.

### The markdown body

Below the header, a full markdown editor with a formatting toolbar:

- **Bold**, **Italic**, **Strikethrough**
- **Horizontal rule**
- **Title** (heading)
- **Link**, **Quote**, **Inline code**, **Code block**
- **Comment** (markdown comment that doesn't render)
- **Image**, **Table**, **List**, **Checked list**
- **Help** (toolbar reference)
- **Edit / Live preview** toggle
- **Fullscreen**

The body holds the skill's spec — what it does, the inputs it expects, the outputs it returns, the side effects, any error modes. Skills are markdown-documented, not code-only; the documentation is what the agent reads.

Save & publish. The skill is now selectable in any agent's Settings.

## Start from a template

If you don't know where to begin, hit **Import skill**. The Templates library lists 72 starter skills across 17 categories — `autonomous-ai-agents`, `blockchain`, `creative`, `devops`, `email`, `finance`, `health`, `mcp`, `mlops`, `productivity`, `research`, `security`, `web-development`, and more. Pick the card closest to your need; the Skill Builder opens with the template pre-filled. Edit name, description, and body, then save.

The full category breakdown:

- `mlops` ships the most (25 templates) — vector DBs, embeddings, fine-tuning helpers, FAISS, Pinecone, Qdrant, Whisper, PyTorch Lightning.
- `research` has 9 — web search, OSINT, drug discovery, bioinformatics.
- `finance` has 7 — DCF, LBO, comps, merger models, Excel and PowerPoint authors.
- `productivity` has 7 — Shopify, SiYuan notes, Telegram, telephony.
- `creative` has 5 — Blender, hyperframes, kanban video orchestration, meme generation.

Templates are starting points. Most teams customise the description and body significantly; the field structure stays the same.

## Connect an MCP server

<Figure
  src="/img/screenshots/mcp-servers.png"
  alt="MCP Servers tab inside Skills & Tools with Vault and Add Server controls"
  caption="MCP Servers tab — Vault stores credentials; Add Server registers an MCP endpoint."
/>

Build → Skills & Tools → **MCP Servers** tab → **Add Server**. The form covers the full MCP wire details.

### Transport

- **HTTP** — the server listens on an HTTPS endpoint. Most vendor MCP servers use this.
- **Stdio** — the server is a local process invoked over stdin/stdout. Used for tooling that runs in the same trust boundary as Surogate.

### Auth method

- **None** — the server accepts unauthenticated calls. Rare; only use for genuinely public tools.
- **OAuth** — full OAuth flow. The server registers an OAuth app; Surogate stores the client credentials in the [Vault](../admin/credential-vault.md).
- **API Key** — a single API key passed in a header. The simplest auth model.
- **Bearer Token** — a bearer token. Functionally similar to API key but distinct in protocol terms.

### Timeout

How long Surogate waits for the server to respond before treating the call as failed. Defaults to 30 seconds; raise for long-running tools (PDF generation, large queries).

### Configuration scope

The same scope model as the [Credential Vault](../admin/credential-vault.md):

- **Platform** — every user in the install can attach this server to their agents.
- **Org** — only users in the specified organisation can.
- **User** — only the registering user can.

Pick the narrowest scope that works. Most internal MCP servers are org-scoped.

Save. The server's tools become selectable on every agent's settings page within the chosen scope.

## Attach to an agent

Open the agent → **Settings** → multi-select your skills and MCP servers → redeploy.

**Agents pin to the version of each skill that exists at deploy time.** Editing a skill creates a new version row but does not propagate to deployed agents. To push an update: save the new version, open each agent that uses the skill, re-select it from the dropdown (the new version is now top of the list), and redeploy.

The pin behaviour is what lets you ship safely: a skill edit doesn't accidentally change the behaviour of every production agent. The cost is the explicit redeploy.

## Schema validation

Skills are typed. The body specifies input and output schemas (usually JSON Schema in a fenced code block). When the agent calls the skill, the schemas are validated:

- **Inputs** — the agent's call must match the input schema. A mismatched type returns a validation error to the agent, which usually retries.
- **Outputs** — the skill's return must match the output schema. A mismatched return raises a runtime error visible in the session trace.

A skill with no schema works (the agent calls it with whatever it wants, the return is unchecked) but loses the type-safety advantage of skills over raw model output. Always declare schemas.

## Publish to the Hub

A polished skill can be published to the [Data Hub](./hub.mdx) as a Skill-kind repo. From the skill's detail → **Publish**. Pick the repo path (defaults to your team's namespace), pick a visibility scope. The skill becomes importable by other Surogate Ops installs that have access to the repo.

Publishing makes sense for skills with broad applicability — generic GitHub tooling, generic data-warehouse query helpers. Keep team-specific skills (with your team's data formats baked in) private.

## When this isn't worth doing

- **A one-shot function call you'll never reuse.** Inline the logic in the agent's system prompt; don't author a skill for a single-purpose hack.
- **Something the model can do natively.** "Reformat this paragraph" is not a skill. Let the model do it directly.
- **Something already wrapped in an MCP server.** Don't re-author what's already accessible; just register the MCP server.

## When something fails

- **Agent doesn't call the skill it should.** The Description isn't specific enough. Rewrite it to say exactly when the skill applies; agents are good at following precise descriptions.
- **Agent calls the skill at the wrong times.** Same root cause, opposite direction. The description suggests the skill is broader than it is. Tighten it.
- **MCP server times out.** Open a session that called it — the timeout shows up there with the URL it tried. Either the server is genuinely slow (raise the timeout), or it's unreachable from Surogate's network (firewall / VPN issue).
- **Schema rejects valid inputs.** Mismatched types in the Skill Builder. Common cause: a `string` field that should be a number, or vice versa.
- **OAuth handshake fails on first attach.** The OAuth app registration in the vendor's system is missing the right redirect URI. Surogate's redirect URI is shown on the MCP server config page; copy it into the vendor's app config.
- **Skill works in test, fails in production.** Most often a credential scope mismatch — the test skill resolved a user-scoped Vault entry that's not visible to other team members. Move the credential to org scope.
